# 候选人工反馈 v0.1

日期：2026-10-23。

## 功能

候选卡片新增“记录人工反馈”，支持同事件、非同事件、待核实与最多1000码点人工备注。默认待核实，只有显式保存才落盘；不把用户之前口头确认自动写为具体作品对判断。

反馈绑定双方账号ID、作品ID、source SHA和服务端候选检索版本。保留所有历次判断；材料或检索版本变化后旧反馈显示“需重新核验”。新反馈不会覆盖旧记录，不会自动勾选原对比确认，不创建事件组，也不改变候选排序、隐藏候选或调用模型。

## 文件与接口

- 新增 `api/services/event_feedback_service.py`：请求校验、当前材料校验、独立元数据、追加记录、幂等及并发冲突。
- 修改 `api/routers/monitor.py`：新增GET/POST `/api/monitor/event-comparison/feedback`，校验自有/竞品角色和关联关系。
- 修改 `webui/src/lib/eventComparison.ts`：反馈客户端和类型。
- 新增 `webui/src/components/monitor/EventCandidateFeedback.tsx`：原位表单、保存/错误状态、历史及重新读取。
- 修改 `webui/src/components/monitor/EventCandidates.tsx`：按作品输入SHA挂载反馈组件。
- 新增 `tests/test_event_feedback.py`；修改 `tools/accept_event_comparison.py` 增加隔离浏览器反馈验收。
- 本文档。

GET参数：双方账号ID、作品ID、当前来源SHA。响应包含最新revision、记录列表、每条source_current与范围说明。GET不创建文件或表。

POST包含双方现有Selection、decision、note、expected_revision、save_key。服务端再次校验当前材料。相同save_key和请求返回原记录，不重复插入；相同key不同请求拒绝409。expected_revision冲突409，不覆盖。前端保留未提交输入，必须显式重新读取后才能基于新版本保存；失败重试保留原请求幂等键。

## 存储与边界

采集库仅以现有只读方式校验，反馈写入采集库同目录独立的 `event_feedback.db`。显式首次保存创建独立SQLite文件及event_feedback表，未接入采集库全局建表或修改采集库Schema。防止元数据路径/硬链接指向采集库。保存事务使用BEGIN IMMEDIATE和唯一键，API只提供追加接口，不提供修改/删除历史。

当前是本地工作台，不新增身份认证，不把记录伪装成可审计的具名多用户签署。已保存反馈不代表平台事实、视频核验或账号整体覆盖。

源库与元数据是两个独立数据库，没有跨库原子性承诺：写入前后校验来源和角色。如保存后重检发现变化，可能记录已经追加但请求返回冲突；重新读取时显示来源失效，不能当作当前有效结论。来源已消失或旧SHA不合法时读取请求拒绝，历史保留在元数据中；本期未提供失效/已删除作品的独立归档浏览页。
