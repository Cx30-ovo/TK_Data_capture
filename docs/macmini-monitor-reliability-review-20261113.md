# Mac mini 持续监控诊断与优化建议

检查日期：2026-11-13（北京时间）。本文记录本次检查时的状态，不代表之后状态持续不变。

## 1. 结论

当前不能把该部署判定为“持续监控正常”。主项目进程和网页 API 仍然存活，但采集已经进入浏览器恢复等待。重复重启后端没有消除评论异常；本轮没有再次重启或修改远端服务。

已经把故障范围缩小到两条链路：

1. 评论任务反复出现 unknown，现有日志未保存足以确定根因的异常细节。
2. 后续发现任务和恢复任务停在 Playwright 建立 CDP 连接的阶段。Chrome 本机 HTTP 调试接口和原始 WebSocket 的 Browser.getVersion 都能响应，但不能由此证明 Playwright 可正常附着页面。

没有发现足以将本次故障认定为抖音平台风控的直接证据。浏览器连接失败之前的评论异常也不能仅凭 unknown 排除平台限制。

## 3. 远端只读核对

### 3.1 服务存活与业务可用不一致

- 网页健康接口返回 ok。
- 执行状态却为 discovery/error，最近操作耗时 90 秒。
- paused=false，但 recovery.pending=true，state=waiting，检查时 attempts=7。
- 暂停标记为 false 不等于采集正在正常推进。

现有源码中，恢复 pending 会让常规监控循环直接返回。因此此时发现、快照和评论不会按正常循环继续执行，等待浏览器恢复。

依据：远端执行状态接口；远端 api/services/monitor_service.py:723；本地 api/main.py:148 的健康接口仅返回固定 ok。健康改造应保留存活探针语义，另设业务就绪或业务健康指标，避免业务退化触发无休止进程重启。

### 3.2 故障卡在 CDP 连接阶段

- output/crawler.log 在 14:50:26、15:01:12 等时刻记录“Connecting to browser via CDP”，对应失败周期未出现成功连接记录。
- Chrome 调试 HTTP 接口可以读取版本和目标列表。
- 原始调试 WebSocket 可以完成连接并返回 Browser.getVersion。
- 检查时有两个抖音页面目标；目标数量本身不足以判断内存泄漏或页面损坏。

这说明不能把当前 network_timeout 直接解释为“访问抖音的网络超时”。当前证据指向 Playwright/CDP 附着链路，但仍未确定是页面目标、Chrome 状态、驱动兼容还是其他初始化问题。

现有恢复流程需要先成功附着浏览器，再执行采集页重置。若卡在附着步骤，无法到达后续重置逻辑；反复执行同一路径可能持续失败。

依据：远端 tools/cdp_browser.py:509；api/services/monitor_service.py:170、547；tools/douyin_collection_page.py:48；output/crawler.log 上述时刻记录。

### 3.3 评论存在真实积压，unknown 无法定位根因

评论数据库以 SQLite mode=ro 读取，未调用会初始化或更新存储的仓库接口。

| 评论任务状态 | 数量 |
| --- | --- |
| completed | 87 |
| expired | 179 |
| partial | 187 |

187 个 partial 任务的保存错误码均为 unknown。库中合计保存 24,731 条主评论和子评论，涉及 333 个作品。

这些是检查时队列存量，不是本份日志中的失败次数，也不是新增评论数。completed 表示程序记录的分页完成状态，不能保证获得平台隐藏或不可访问的评论。

队列中保留的是通用提示，后台日志也未在对应失败处提供可用的原始异常堆栈。因此不能将 187 个任务全部归到风控、超时或同一程序错误。

还发现一个调度风险：独立评论任务先初始化浏览器，随后才进入 collect_one 中的队列认领。如果初始化阶段失败，可能未更新该作品的下次重试时间，导致下个循环再次选中同一作品。这个风险与部分重复告警的节奏相符，但尚未证明每条告警均由它造成。

依据：远端 api/services/monitor_service.py:1053；api/services/monitor_comments_service.py 的 collect_one；database/monitor_comments_repository.py:183；只读评论队列聚合。

### 3.4 托管与运行环境

- 主项目以独立后台进程运行。所查用户 LaunchAgents 和系统 LaunchDaemons 中未找到直接托管该项目目录的配置；不能据此排除其他外部守护方式，但当前未证明进程退出后能自动拉起。
- 同机还有另一目录下的 API 进程。其监控状态接口未成功返回，不能据此认定它在重复采集；不应直接停止它。
- 电源策略的系统 sleep 为 0，本次未发现因配置了系统自动睡眠而中断的证据。
- 本地已有监控调度改动，远端仍走旧的快照内联评论流程。不能把“本地已改”视为“Mac mini 已应用”，也不应直接全量覆盖含其他未验收改动的工作区。

## 4. 建议修复顺序

| 优先级 | 工作 | 验收重点 |
| --- | --- | --- |
| P0 | 细分初始化阶段，记录脱敏异常类别、堆栈位置、任务种类和关联 ID | 下一次失败能确定发生在 CDP 连接、目标附着、页面导航、登录检查、评论主分页、子分页还是写库 |
| P0 | 浏览器恢复分级：连接诊断、受管采集目标恢复、专用浏览器恢复 | 避免依赖失败的同一附着路径；只处理确认属于项目的目标和专用实例，保留登录目录，不操作其他服务或浏览器 |
| P0 | 评论初始化失败也纳入队列退避；单作品失败不阻塞其他任务 | 不无限重复选择失败项；游标保存，有限重试，失败后可继续恢复 |
| P1 | 发现、快照优先，评论排队分片；统一浏览器互斥与请求节奏 | 评论大队列不拖延作品发现和到期快照；不会通过并发增加平台请求压力 |
| P1 | 分离 API 存活和采集业务健康；按任务记录最近成功与积压年龄 | 页面显示服务存活但采集退化；没有新作品时，成功检查仍更新检查健康指标 |
| P1 | 为主项目建立单实例进程托管及有界重启策略 | 意外退出后拉起；用户暂停、登录失效和风控冷却不能触发无休止重启 |
| P1 | 持久化必要的冷却、重试与恢复状态 | 重启不绕过现有冷却，不丢评论游标；恢复时处理运行中遗留任务 |

浏览器恢复不能绕过登录、验证码或平台限制。现有风控冷却配置本轮未改变，优化也不应靠提高请求频率实现。

## 5. 建议验收

先在隔离环境验证，再小范围部署；本次检查没有实施这些改动。

1. 模拟 HTTP 调试接口和原始 WebSocket 正常、Playwright 附着超时，验证阶段诊断与有界恢复。
2. 模拟评论初始化异常、主评论失败、子评论失败、空响应和数据库忙，确认分类、退避及游标保留。
3. 模拟单作品长期失败，确认其他作品发现和快照可以继续；浏览器整体不可用时必须如实显示全局退化。
4. 模拟后台进程退出、浏览器退出与重启，验证单实例、进程托管和中断任务回收。
5. 模拟登录失效、用户暂停和风控冷却，确认不会自动绕过或重启清除状态。
6. 按快照窗口区分“仍可补采”和“已错过”，不以恢复后的当前数据冒充过去时点快照。
7. 连续观察至少 24 小时，覆盖发现周期、快照到期、评论分页、备份和恢复。记录成功检查率、最大延迟、积压年龄及恢复时长；人工暂停、平台限制和网络中断分别登记。

不能保证外部平台和网络永不故障。持续监控能力的目标应是故障可识别、重试有边界、数据与游标保留、恢复可验证，而不是仅保证进程在线。

## 6. 本轮操作范围

- 读取用户附件及相关本地源码。
- SSH 只读核对远端状态、日志、指定源码、电源策略和托管配置。
- 对 Chrome 本机调试端点执行只读查询及 Browser.getVersion，没有导航作品页或发起新的平台采集。
- 评论数据库只读聚合，没有写正式库。
- 未修改业务源码，未重启、暂停、恢复、部署或修改 Mac mini 配置；未调用模型。
- 本报告不记录内网地址、域名、服务端口或凭据。
