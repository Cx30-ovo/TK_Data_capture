# 子评论响应诊断与续采修复

日期：2026-11-17。本次为本地代码修复；未部署或重启远端服务，未调用模型、主动请求平台或操作正式库。

## 诊断结论

前次只读检查将8条告警逐条关联到子评论页的列表校验。历史日志未保存comments的具体类型、total及has_more，因此不能确定是线程不可见、平台格式变化、临时限制还是其他原因，也不能认定为风控。

代码复核确认两个本地缺口：

1. 子评论页格式异常会退出整个作品的采集，后面的主评论线程也无法继续。后续重试仍从同一失败线程开始。
2. 原错误分类按“分页状态”文本命中tab_changed，可能把响应格式异常误报为页签切换。

## 修复内容

- `tools/collection_errors.py`：增加有明确类型的CommentResponseError。日志仅保留字段白名单的存在性、类型、安全范围内的整数/布尔值、数组长度，以及作品/线程哈希和请求游标；不记录完整响应、任意键、文本、签名、凭据或完整URL。结构诊断只进日志，不添加到公开错误摘要。
- `api/services/monitor_comments_service.py`：严格验证成功状态、明确分页状态和列表；明确空结果仅接受整数total=0且has_more明确为false/0。保留现有缺失status_code时处理合法列表页的兼容行为，诊断会区分字段缺失与实际返回0。
- 修正格式异常的分类优先级，不再把本次带类型的缺分页状态异常归为页签切换。
- 对列表/分页形状错误和游标不前进，保存失败线程的原游标至既有checkpoint.reply_pending，同时推进正常线程扫描位置；失败页不写入，不把失败线程标完成。其他线程仍可在原有时间片内继续。
- 正常扫描结束后轮转续采待处理线程。每个失败线程在同一时间片最多失败一次；分页成功则继续该线程，跨时间片保存最新已提交游标。待处理集合清空且扫描结束才标记replies_done。
- 全局异常（风控、非成功状态、非对象响应、连接/超时、策略关闭、停止、存储错误）仍立即停止请求，不进入线程跳转。身份校验错误也不被当作可跳转的格式错误。
- 请求间隔、每时间片10次请求上限、总超时和既有失败退避不变；没有取消三小时风控上限或人为增加请求预算。

## 数据与兼容边界

仅扩展既有JSON checkpoint的可选字段reply_pending和reply_scan_done，仍读取version=1的旧检查点。不新增表、列、索引或迁移，不改仓库DDL。新待续采线程与正常扫描位置同事务保存；写入失败不跳过该线程。暂停、取消、进程重建后仍可恢复。

既有评论不删除、不重复计入；成功页继续通过既有upsert存储。输入计数为0不用于跳过线程，仍检查平台可见的每个主评论线程。

旧版采集器不认识新增的待续采集合。以后如部署后需要回退，不应让旧版直接接管尚有reply_pending的队列；应保留数据库和检查点，在暂停评论采集的窗口内另行核对安全重遍历方案，不删除队列或把未完成线程标成功。
