## 诊断依据与结论边界

此前附件的224条唯一评论告警中，217条异常最终落在评论库提交，另7条为平台响应未满足评论分页格式校验。原诊断见 `tmp/monitor-log-review-20261116-01/log-review-report.md`。

隔离测试已复现：DELETE日志模式下，下游长期保持源库读事务，并在其中等待目标库操作，会导致源库写事务提交失败，错误码为SQLITE_BUSY。新同步候选移除这一长事务路径。

历史217条异常没有保留SQLite错误码，不能据复现实验将其全部追认为锁竞争；需要上线后新增诊断核对。7条无效响应的判定不变，不将不完整响应当作零评论或采集完成。

## 主项目变更

| 文件 | 用途 |
|---|---|
| `database/monitor_comments_repository.py` | 对明确的SQLITE_BUSY/SQLITE_LOCKED及其扩展码执行最多3次本地事务尝试；每次失败先回滚、关闭连接，再重试；记录实际存储阶段。评论行与续采游标原子保存，生成器输入在重试前固定。首次初始化DDL与写入同一事务，DDL定义不变。 |
| `tools/collection_errors.py` | 新增storage_busy/storage_error分类；白名单记录SQLite错误码、名称、尝试次数与存储阶段，不记录异常正文、URL、凭据；不把SQLite异常文本误判成平台风控。 |
| `tests/test_comment_storage_contention.py` | 19项真实SQLite锁竞争、事务原子性、取消、游标、错误分类与陈旧任务恢复边界测试。 |

写连接每次SQLite忙等待为0.25秒，两次重试间隔为0.05/0.15秒；只重做本地数据库事务，不在重试装饰器内重发平台请求。磁盘满、只读和IO错误不做锁竞争重试。该设置不是整个业务操作的严格总耗时上限。

不修改表、列、索引、既有DDL定义，不迁移、不切换WAL。既有600秒陈旧running重新认领规则不变，测试验证账号隔离、保留游标、不抢占新鲜running。
