# 话题首轮采集与状态修复

日期：2026-11-02。后端版本 `topic-monitor-v0.1.1`，前端独立产物 `webui/dist-topic-monitor-first-run-20261102-01`，已本地生效。

## 核对与原因边界

真实任务创建时间与首次领取时间相差约2秒，说明不是需要等待完整60分钟才开始。此前轮次遗留为running，但内存没有对应执行任务，页面仍显示空闲/持续监控，缺少真实阶段提示。

本地还观察到替代后端在已占用的监听地址启动失败。离线测试复现了一个相关执行漏洞：`asyncio.to_thread` 领取事务提交期间，协程被取消，线程仍会完成领取，旧实现可能遗留running轮次。不能仅凭端口冲突记录，将此前每条中断唯一归因为同一原因。

另有两项代码缺口：新建任务没有主动唤醒轮询器；运行租约过期/显式中断后，原间隔检查仍可能阻止及时恢复。此次同时修复。

## 变更

- 启用的新任务创建成功、或启用已有任务后，主动唤醒空闲调度器；创建暂停任务不唤醒采集。发布时间在未来的任务仍等待窗口开始。
- 浏览器忙、全局暂停、登录恢复及风控冷却继续生效；仍使用共享互斥锁，不抢占账号采集。话题轮次后的65秒账号轮询保护窗口保留，因此“尽快开始”不代表绕过正在执行的任务或保护窗口。
- 页面按话题展示排队、连接、搜索关键词进度、已搜索页数、等待账号采集、等待间隔及异常轮次恢复状态；每5秒读取进度。
- 列表增加 worker_running、worker_version 和逐任务 collection 状态，均为只读；不由GET触发采集。
- 将采集适配器初始化纳入错误收尾；先记录失败再执行恢复副作用；安全日志记录错误类型及代码位置，不记录请求正文/地址/凭据。
- 领取事务使用可等待的屏蔽取消任务。服务关闭时等待领取线程完成，并将已领取但未开始的轮次正常收尾，避免遗留running。
- 租约过期或已登记interrupted的轮次可恢复，不再被原60分钟间隔挡住。不绕过仍有效的执行租约。
- 不新增表或迁移，不修改账号发现、快照、全局冷却参数。

源码范围：`database/topic_monitor_repository.py`、`api/services/topic_monitor_service.py`、`webui/src/lib/topicMonitor.ts`、`webui/src/components/monitor/TopicMonitor.tsx`；测试范围：`tests/test_topic_monitor.py`、`tools/accept_topic_monitor.py`。
